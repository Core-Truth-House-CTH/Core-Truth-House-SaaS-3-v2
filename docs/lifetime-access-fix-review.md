# Lifetime access and claim frontend patch

Worktree: `/root/cth-standard-frontend`, branch `fix/standard-cohort-enrollment`. Earlier Standard enrollment patch preserved. No live files, configuration, services, credentials or customer records used.

The authenticated, workspace-scoped plan API's `effective_access` object establishes lifetime access only when plan is `estate`, lifetime is boolean true, and active is boolean true. No URL, workspace field or Clerk unsafe metadata establishes lifetime access. Removed the pre-existing workspace-name access override and unsafe-metadata role fallback. Existing backend-authorized roles and PlanGate admin restrictions remain. Billing displays lifetime Estate access separately from the real subscription status, including cancelled/unpaid states.

The dedicated claim route sits inside authentication and outside paid-plan gates. The server checks ownership and grants access; the frontend sends the selected workspace explicitly and requires `{success: true, workspace_id: selectedWorkspace}` before considering the claim successful. Workspaces and canonical plan data refresh before navigation. Network failures, false/mismatched success responses and refresh failures retain the claim for retry. The button/ref prevent duplicate in-flight submissions in a mounted screen; server-side atomic binding supplies cross-tab/concurrent safety.

Fresh links use `/cohort/join#token=...`, with compatibility for existing `/cohort/join/:token` links. Validation/redemption send the token in POST bodies rather than HTTP paths. Claim tokens are stored in same-tab sessionStorage before sign-in/sign-up; auth redirects do not contain them. Legacy command-center query links are captured and removed before authentication. Failed attempts retain the token; success removes only the same token so an old completion cannot erase a newer link. No-referrer metadata prevents bearer links leaking via referrer headers; claim error reporting contains no URL/provider details. Existing legacy links already delivered with path/query tokens can still appear in the initial hosting access log; the new flow cannot retroactively change those initial requests. Session storage must be enabled; otherwise the claim stops with a clear message and retains the original link.
